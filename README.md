# Task Service

Сервис управления задачами с возможностью настройки периодического создания задач (ежедневно, ежемесячно, по конкретным датам, чётные/нечётные дни).

## Быстрый запуск

```bash
docker compose up --build
```

- API: `http://localhost:8080`
- Swagger UI: `http://localhost:8080/swagger/`

Если нужно пересоздать БД:

```bash
docker compose down -v && docker compose up --build
```

---

## Что было реализовано

К существующему CRUD API задач добавлена фича периодичности: пользователь может указать расписание, по которому задача будет автоматически создаваться повторно.

### Типы периодичности

| Тип | Описание | Обязательные поля |
|---|---|---|
| `daily` | Каждые N дней | `days_interval` (≥ 1) |
| `monthly` | Каждый месяц в определённое число | `day_of_month` (1–30) |
| `custom` | Только на указанные даты | `custom_dates` (массив дат) |
| `even_odd` | Чётные или нечётные дни месяца | `even_odd` (`"even"` или `"odd"`) |

### Примеры запросов

**Ежедневная задача (каждый день):**
```json
POST /api/v1/tasks
{
  "title": "Ежедневный обход пациентов",
  "status": "new",
  "periodicity": {
    "period_type": "daily",
    "days_interval": 1
  }
}
```

**Ежемесячная задача (15-го числа):**
```json
{
  "title": "Формирование отчёта",
  "status": "new",
  "periodicity": {
    "period_type": "monthly",
    "day_of_month": 15
  }
}
```

**Задача на конкретные даты:**
```json
{
  "title": "Запланированная встреча",
  "status": "new",
  "periodicity": {
    "period_type": "custom",
    "custom_dates": ["2026-04-15", "2026-05-01", "2026-06-10"]
  }
}
```

**Задача по чётным дням:**
```json
{
  "title": "Прием медикаментов",
  "status": "new",
  "periodicity": {
    "period_type": "even_odd",
    "even_odd": "even"
  }
}
```

## Принятые архитектурные решения

### 1. Отдельная таблица `periodicity`

Настройки периодичности хранятся в отдельной таблице `periodicity` с `task_id` как первичным ключом (связь 1:1), а не в колонках таблицы `tasks`, чтобы разделять сущности: задача и расписание — разные сущности.

### 2. `last_created_at` для предотвращения дубликатов

В таблицу `periodicity` добавлена колонка `last_created_at TIMESTAMPTZ`. Scheduler проверяет, создавалась ли уже задача **сегодня**, и если да — пропускает.

### 3. Транзакции для Create и Update

Операции с `tasks` и `periodicity` обёрнуты в одну транзакцию. Если сохранение расписания упадёт — задача тоже откатится.

### 4. Валидация полей периодичности

Если тип `daily`, но в запросе переданы `even_odd` или `day_of_month` — они **игнорируются**. Валидация проверяет только поле, соответствующее типу:

```go
// daily → проверяет только days_interval
// monthly → проверяет только day_of_month
// custom → проверяет только custom_dates
// even_odd → проверяет только even_odd
```

### 5. Формат дат

Даты в `custom_dates` принимаются и отдаются в формате `"2006-01-02"` (ISO-дата без времени).

### 6. Нечувствительность к регистру для `even_odd`

Значение `even_odd` приводится к нижнему регистру на уровне usecase:

```json
"even_odd": "Even"   →   "even"
"even_odd": "ODD"    →   "odd"
```

## Планировщик

### Принцип работы

Планировщик — это фоновый процесс, который:

1. Каждые **20 минут** загружает из БД все задачи-шаблоны (те, у которых есть запись в `periodicity`)
2. Для каждого шаблона проверяет, **должна ли задача быть создана сегодня**:
   - `daily` — прошло ли N дней с момента создания шаблона
   - `monthly` — совпадает ли сегодняшнее число месяца с `day_of_month`
   - `custom` — есть ли сегодняшняя дата в `custom_dates`
   - `even_odd` — чётный/нечётный ли сегодня день месяца
3. Если день подходит и задача ещё **не создавалась сегодня** (проверка `last_created_at`):
   - Создаёт новый экземпляр задачи со статусом `new`
   - Обновляет `last_created_at` в таблице `periodicity`
